# 生活决策工具箱 · 产品需求文档

> 文档版本：v0.1｜日期：2026-10-08｜状态：待评审，未进入实现与发布
>
> 产品工作名：生活决策工具箱，非正式品牌名。沿用当前微信小程序作为实现载体；「真涨薪」保留为 Offer 对比工具。本文只定义扩展需求，不代表相关能力已经上线。

## 1. 产品定义

### 1.1 一句话定位

面对一件具体的生活选择，帮助用户算清代价、发现遗漏、明确下一步，不替用户做决定。

长期覆盖工作、居住、学习和家庭准备等决策；首版聚焦正在换工作、搬家或考虑短暂停工的职场用户。

### 1.2 用户真正需要的结果

- 已经算清：金钱、时间及其差异，而不是含糊的“更划算”。
- 成立条件：输入、假设和口径变化时，结论如何变化。
- 尚未确认：未知数据、无法量化的偏好、需要核实的事项。
- 下一步：与当前问题直接相关、数量有限的行动。

成功不是用户服从推荐，而是能复述关键取舍，并补查一个影响决定的信息。

### 1.3 产品原则

1. 可计算的精确算，不确定的明确说；不生成“人生最优解”。
2. 先判断硬性条件，再看成本差异；不把健康、关系、成长等强行换算成统一分数。
3. 按用户遇到的问题组织入口，不按知识库章节组织首页。
4. 每个场景独立完成，不把多个场景合成一个越来越长的表单。
5. 默认本地计算和保存，不要求登录，不上传薪资、存款与预算。
6. 需要时展开依据，不让内容阅读挡在计算前面。
7. 不为增加使用频次添加打卡、每日推荐、积分或焦虑提醒。

### 2.3 核心假设与风险

核心假设：在 Offer 以外的具体生活选择中，用户愿意填写少量信息，并认为透明的结构化比较比自行心算、搜索或泛泛问答更有帮助。

| 风险 | 影响 | 首轮验证方式 |
| --- | --- | --- |
| 用户不愿填写或无法获得数据 | 场景覆盖再多也无法产生可用结果 | 观察真实任务中的退出点和缺失字段 |
| 内容多但不能改变实际行动 | 退化为资料库 | 回访是否核实信息、调整方案或拿结果讨论 |
| 数字制造错误确定性 | 用户把估算理解为推荐或安全保证 | 要求参与者复述口径，检查误解来源 |

目前没有足够的用户证据证明需求强度、付费意愿或留存效果；不使用虚构市场规模或主观产品评分代替验证。

## 3. 用户与使用场景

### 3.1 首批用户

近期确实有换工作、租房搬家或停工计划的国内职场用户。无需先限定年龄、行业或收入水平；招募以真实问题是否正在发生为准。

### 3.2 用户故事

| 编号 | 用户问题 | 产品应帮助完成 |
| --- | --- | --- |
| US-01 | 工资涨了，但工时和通勤也变长，值得换吗？ | 对比保证收入、公司公积金、时间占用及追平条件 |
| US-02 | 多花房租住近一点，到底是在用多少钱换时间？ | 对比两处住处的月成本与通勤时间 |
| US-03 | 暂时没有工资，现有资金能覆盖多久？ | 在明确预算假设下估算可覆盖月数 |
| US-04 | 上次填了一半，想继续或改个数字 | 恢复同场景草稿并重新计算 |
| US-05 | 想把工具发给朋友，但不想泄露收入和存款 | 分享空白场景入口 |

### 3.3 长期能力类型

| 类型 | 适用问题 | 产品形态 | 首版范围 |
| --- | --- | --- | --- |
| 算清成本 | 收入、租房通勤、空窗期 | 确定性公式、差异、假设 | 三个场景 |
| 理清取舍 | 换城市、转行、学习投入 | 硬性条件、代价、待确认信息 | 只提供场景内静态核对提示；不做通用编辑器 |
| 准备行动 | 搬家、入职、离职手续 | 有来源、有适用条件的清单 | 每个结果最多三条优先提示；不做独立任务系统 |

## 4. 版本范围与优先级

### 4.1 V1 必须交付（P0）

- 三场景首页：Offer 对比、租房通勤、空窗期预算。
- 保持原 Offer 计算与反超功能可用，并解释缺失公积金数据。
- 两个新增场景的输入、校验、结果、重新编辑闭环。
- 每场景仅保存一份当前草稿；支持继续与明确清除。
- 计算假设、缺失信息和最多三条相关核对提示。
- 内容来源说明及入口分享，不分享个人结果。
- 小屏、长数字、软键盘、安全区与基础无障碍验收。

### 4.2 先不交付

- 全量导入 HowToLiveBetter、全文搜索、内容推荐流、每日一读。
- AI 聊天、自动替用户选择、统一人生评分、自动偏好权重。
- 全国税后工资计算器、社保政策库、城市生活成本数据库。
- 买房/投资推荐、医疗诊断、法律结论或权益领取资格自动判定。
- 用户账号、云同步、家庭协作、多份历史方案管理、结果海报/PDF。
- 跨场景自动复用工资和存款、云端埋点、消息订阅、付费与广告。

### 4.3 后续候选（均非承诺）

先根据验证结果选择“换城市成本”或“学习投入”中的一个，不同时扩展。跨场景联动、自然语言入口和报告导出另立需求，不在 V1 预建配置平台或万能计算引擎。

## 5. 信息架构与通用流程

### 5.1 页面结构

```text
场景首页
├─ 换工作怎么算 → 现有 Offer 输入 → 对比结果 → 反超试算
├─ 住近一点值不值 → 住处 A / B 输入 → 通勤成本结果
├─ 暂时不工作能撑多久 → 现金与月预算输入 → 预算结果
└─ 来源与隐私说明

各结果页 → 修改输入 / 查看计算口径 / 查看相关依据 / 分享场景入口
```

以上为产品页面结构，不限定代码路由或组件拆分。首版无需 TabBar；“返回首页”是辅助动作，不与计算主按钮争抢位置。

### 5.2 首页（FR-01）

- 标题“你正在考虑什么？”；三张场景卡，每张一个清晰问题和一句说明。
- 已有草稿的卡片显示“继续填写”或“查看上次结果”，不显示金额。
- 无草稿不显示空的历史记录区；首页不展示尚未开放的场景。
- 常规启动进入首页；已有 Offer 分享路径继续有效，直接进入 Offer 场景，不强制经过首页。

### 5.3 输入（FR-02）

- 每场景最多两步；租房以“住处 A”“住处 B”分步，保留切换和修改能力。
- 不设置重复的数字预设选项卡；字段直接填写、清楚标注单位。
- 必填缺失可保存草稿，但不能生成正式结果；错误就近展示，提交时定位首个错误。
- 新场景不预填看似真实的个人金额。示例必须由用户主动触发，已有输入时确认覆盖，示例状态明确标记。
- 结果只基于显式输入或清楚列出的假设。字段允许填 0 不代表空白等于 0。

### 5.4 结果（FR-03）

所有场景采用同一信息顺序，具体布局可不同：

1. 一句事实摘要和不超过三个主要指标。
2. 计算明细与输入假设，默认收起长解释但保留口径提示。
3. 尚未确认的条件；最多三条与场景相关的优先核对事项。
4. 主动作“修改条件”；分享作为次级动作。

不得出现“最佳人生选择”“放心辞职”“一定更值得”等越过计算边界的文案。计算失败不能退回示例值或复用不对应当前输入的旧结果。

### 5.5 保存与恢复（FR-04）

- 每场景一份当前草稿；失焦、切换步骤或正常离开时保存有效输入状态，非法或未完成值也作为草稿保留，但不用于计算。
- 修改输入后，旧结果标记失效；再次查看前重新校验、计算。
- 返回首页可继续；重开小程序恢复草稿，不能把示例标记丢掉。
- “重新填写”清除该场景，需确认；“清除本机数据”列明影响三个场景并二次确认。
- 存储失败时仍允许当次计算，明确提示“结果可查看，但本次未能保存”。

## 6. 场景一：Offer 对比（FR-05）

### 6.1 输入与范围

沿用当前工作与一至两个 Offer 的字段、校验范围和两两比较能力。输入包括税前月薪、全年固定发薪月数、另有保证奖金月数、每周工时、单程通勤，以及可选的五险/公积金基数和公司公积金比例。

### 6.2 公式与口径

```text
税前保证年收入 = 税前月薪 ×（固定发薪月数 + 另有保证奖金月数）
公司公积金年缴存 = 公积金基数 × 公司比例 ÷ 100 × 12
年综合价值 = 税前保证年收入 + 已知的公司公积金年缴存
年度占用时间 = 每周工时 × 48 + 单程通勤分钟 × 2 × 240 ÷ 60
综合时薪 = 年综合价值 ÷ 年度占用时间
```

- 年度 48 工作周、240 通勤日沿用现有假设，可查看；V1 不新增可配置入口。
- 五险基数单独展示，不算作用户收入。
- 固定发薪月数中已包含的奖金不能在“另有保证奖金”重复填写，字段旁明确提示。
- 公司公积金不等于工资到账，不纳入空窗期可动用现金。
- 公积金任一计算字段缺失时，显示“未计入公司公积金”；不是已确认的 0。
- 对比中有公积金缺失时，摘要注明“按已填写项目比较，部分公积金未计入”；不把这种领先描述成确定的总待遇领先。
- 不估算税后收入、试用期折扣、浮动奖金、股票期权，也不声称评估了岗位稳定性。

### 6.3 结果与保护

保留年综合价值、税前保证年收入、综合时薪、五险一金对比及反超入口。已有反超试算不回写原始数据。扩展首页与新数据结构不能破坏旧草稿和历史分享入口。

## 7. 场景二：租房与通勤（FR-06）

### 7.1 目标

比较两处住处在“每月住房＋通勤支出”和“每月通勤时间”上的差异，解释用多少钱换回多少时间，不评判居住品质。

### 7.2 输入定义

| 字段 | 所属 | 规则 | 说明 |
| --- | --- | --- | --- |
| 方案名称 | A / B | 可选，最多 12 字 | 默认住处 A / B，不要求真实地址 |
| 每月住房总支出 | A / B | 必填，0–1,000,000 元，最多两位小数 | 月租＋物业等固定住房费；水电等波动费用可填本人月均估算 |
| 每月通勤交通费 | A / B | 必填，0–1,000,000 元，最多两位小数 | 按相同通勤天数估算；步行或无支出明确填 0 |
| 单程通勤时间 | A / B | 必填，0–720 分钟，最多一位小数 | 含步行、候车等；建议使用常见高峰实测值 |
| 每月通勤天数 | 两方案共用 | 必填，0–31 的整数 | 首版只比较同一工作安排下的两处住处，不预设 22 天 |

边界值仅为输入保护，不是生活建议。未填金额一律不按零处理；不读取定位、不查地图、不收集地址。

### 7.3 公式

```text
C_A / C_B = 各自每月住房总支出 + 每月通勤交通费
H_A / H_B = 各自单程通勤分钟 × 2 × 月通勤天数 ÷ 60
ΔC = C_B - C_A                    # 正数：B 更贵
ΔH = H_A - H_B                    # 正数：B 更省时间
```

当成本和时间存在取舍时，以“更省时间的方案”为参照：

```text
每节省一小时的额外支出 = 更省时间方案的额外月支出 ÷ 每月节省小时
```

### 7.4 输出分支

| 条件 | 结果文案方向 | 单小时换时间成本 |
| --- | --- | --- |
| B 更贵且更省时间 | B 每月多花 X 元，节省 Y 小时 | 输出正数 X / Y |
| A 更贵且更省时间 | A 每月多花 X 元，节省 Y 小时 | 输出正数 X / Y |
| 一个方案更便宜且更省时间 | 在已填写的支出与通勤上，该方案均更低 | 不输出负数“换时间成本” |
| 成本相同、时间不同 | 月支出相同，某方案少通勤 Y 小时 | 可写“无需增加月支出” |
| 时间相同、成本不同 | 通勤时间相同，某方案每月少花 X 元 | 不除以零，不输出无穷值 |
| 成本与时间均相同 | 已填写的两项指标相同 | 不强行选出优胜方 |

- 通勤天数为 0 时，仍展示住房和用户填入的交通支出，解释通勤时间均为 0；不擅自删除交通月票等费用。
- 房屋条件、噪声、同住人等不计分，也不能因为两个数字领先就宣布“更值得租”。
- 不含押金占用、搬家、中介费和退租损失；结果显著标注“仅比较经常性月支出”，提示有搬迁计划时另核对一次性费用。
- 首版不计算搬家回本期，不自动用 Offer 时薪给用户空闲时间定价。

### 7.5 样例

A：住房 3,000 元、交通 300 元、单程 60 分钟；B：住房 4,000 元、交通 100 元、单程 30 分钟；每月通勤 22 天。

预期：A 月支出 3,300 元/通勤 44 小时；B 月支出 4,100 元/通勤 22 小时。B 多花 800 元、节省 22 小时，每节省一小时额外支出约 36.36 元。

## 8. 场景三：空窗期预算（FR-07）

### 8.1 目标与边界

估算在用户给定的固定月预算下，可动用资金能够覆盖的时长。不是辞职建议、投资建议或财务安全保证，不预测找到工作的日期。

### 8.2 输入定义

| 字段 | 规则 | 说明 |
| --- | --- | --- |
| 当前可动用资金 S | 必填，0–100,000,000 元，最多两位小数 | 已到账、可用于生活的现金/存款；不含信用额度、未到账补偿、预计奖金、公积金余额或待变现资产 |
| 不计划动用的预留资金 R | 必填，可明确填 0，且不得超过 S | 用户自定，不自动推荐比例；已包含在 S 中，不能重复排除 |
| 近期一次性支出 O | 必填，可明确填 0，0–100,000,000 元 | 在预算起点即扣除的已知支出，不再计入月支出 |
| 每月总支出 E | 必填，0–1,000,000 元 | 用户合计房租、生活、还款、自缴保障等；允许 0 但标注确认是否漏项 |
| 每月确定的其他到账收入 I | 必填，可明确填 0，0–1,000,000 元 | 已确认且预计覆盖所算期间的固定到账；不含求职、投资收益或未确认补贴预期 |

所有金额最多两位小数。首版采用总额输入＋核对说明，不要求记账或细分十几个支出字段。收入会在中途停止、支出会分阶段变化时，本模型不适用，应提示分别试算，不宣称已覆盖这些变化。

### 8.3 公式和判断顺序

```text
原始可用预算 B_raw = S - R - O
可用预算 B = max(0, B_raw)
每月净支出 D = E - I
```

1. `B_raw < 0`：优先提示“预留资金与一次性支出超过可用资金 X 元”，不输出覆盖月数，不用未来收入抵消起点缺口。
2. `B_raw >= 0 且 D > 0`：覆盖月数 `M = B / D`；B 为 0 时明确显示 0 个月。
3. `B_raw >= 0 且 D = 0`：显示“按当前月预算收支相抵，未计算资金耗尽时间”。
4. `B_raw >= 0 且 D < 0`：显示“按当前月预算每月结余 X 元，未计算资金耗尽时间”。

第 3、4 种情况均不得显示“无限期休息”或“财务自由”。预算模型忽略月内到账时点，不生成精确耗尽日期；必须说明月底收入不能代表月初账单一定付得出。

### 8.4 结果

- 主要展示可用预算、每月净支出和估算覆盖月数（适用时）。
- 覆盖月数向下保留一位小数，注明保守截取；正数但不足 0.1 个月显示“不足 0.1 个月”。
- 不自动计入任何权益、补贴或投资回报；政策相关内容只提供核对方向，经审核后再链接依据。
- 固定提示：检查大额账单/自缴保障等漏项、确认其他收入持续性、确认一次性支出。
- 不根据月数使用“安全/危险”红绿评分，也不输出辞职建议。

### 8.5 样例

S = 60,000，R = 12,000，O = 6,000，E = 6,000，I = 1,000。

预期：可用预算 42,000 元、月净支出 5,000 元，覆盖 8.4 个月。所有结果均以月预算稳定且其他收入持续为前提。

## 9. 内容接入与可信度（FR-08）

### 9.1 HowToLiveBetter 的角色

作为场景选题和核对提示的参考来源之一，不是个人结论引擎，也不是已替本产品完成核验的政策数据库。V1 只收录与三个场景直接有关的少量提示，不整书导入，不复制其性价比排序作为用户推荐。

计算公式来自本产品的明确口径；引用文章内容与自行设计的计算必须分开标识，不暗示上游作者为本产品背书。

### 9.2 内容记录要求

每条引用提示保存：稳定 ID、适用场景、简短文案、适用地区/人群、上游章节与条目、原始来源链接、来源版本（提交或快照日期）、人工核验日期、限制/争议、改编标记及许可信息。

普通自编的输入核对提示标识为“填写提醒”，不伪造文献或证据等级。

### 9.3 审核与展示

- 接入流程：选条目 → 阅读原始来源 → 核对适用条件与现行状态 → 改写为问题/提醒 → 人工审阅 → 随版本发布。
- 过期、链接失效且无法验证、适用条件不清的政策内容不发布为确定结论；已上线条目发现问题后须撤下或明确失效，并安排版本修复。
- V1 内容随包发布，无自动热更新；发布前复核相关条目，不能承诺实时政策。
- 来源页展示可读的出处摘要、适用范围和核验日期；如无法在小程序内打开原文，提供复制链接，不把任意外链嵌入作为首版依赖。
- 不将“有出处”或上游 A/B/C 标签等同于“适合所有人”；有争议内容不得隐藏争议。
- 发布内容按上游许可保留署名、许可证、改编说明与同步版本。第三方衍生代码的许可另行核验，不默认沿用上游代码许可。

## 10. 隐私、数据与分享（FR-09）

### 10.1 本地数据

- 新场景保存类型、输入、示例标记、更新时间、结构版本和计算版本；无需保存多份历史结果，优先由输入重新计算。
- 三个场景存储命名空间隔离。Offer 旧草稿原位兼容或进行非破坏迁移，迁移失败不清空旧数据。
- 各场景不自动读入其他场景金额；未来如提供复用需显式确认，并重新核对税前/到账口径。
- 本地不等于加密保险箱：不承诺设备级加密；告知卸载、清缓存、换机可能丢失，首版无云恢复。
- 损坏草稿不导致闪退；提示该场景无法恢复并允许重新填写，不删除其他场景。

### 10.2 隐私边界

- 产品代码不向服务端、日志、错误报告或统计接口发送个人输入和结果。
- 不新增广告、分析 SDK、通讯录、定位或相册权限。
- 无需上传个人数据即可完成全部 V1 功能；平台自身处理的数据以平台说明为准，不承诺“整个微信没有网络请求”。
- 未来引入 AI、云同步或统计，必须另行设计告知、授权、删除机制，并更新“本地处理”的承诺；本 PRD 不授权上述能力。

### 10.3 分享

- 仅携带固定场景标识，标题与封面不含用户姓名、方案名称、薪资、存款、输入或结果。
- 接收方使用自己的本地草稿；没有草稿则进入空白表单，不获得发送方数据。
- 来源页复制仅复制公开链接；复制失败应提示，不请求无关权限。

## 11. 交互与视觉验收约束（FR-10）

不在本 PRD 锁定最终视觉稿；设计阶段必须满足以下已知问题约束。

- 延续清爽、克制、数字清晰的方向，不为了新品牌整体重做已稳定页面。
- 数字不被单位、清除按钮或容器裁切；最大合法金额在编辑和结果状态都能完整查看。
- 分段选项文字水平、垂直居中；选中状态不只依赖颜色。
- 固定底栏只保留一个明确主动作；上一步作为次动作，不能挤出主按钮或占用数字宽度。
- 底栏适配键盘与底部安全区，不遮住最后一项；焦点字段、错误提示可滚动到可视区。
- 可选说明自然展开，不出现按钮默认样式导致的窄栏、居中小块或长文挤压。
- 320、375、390、430 CSS px 等效宽度均无横向溢出；iOS/Android 分别检查。
- 正文与背景保持可读对比，普通文本以 4.5:1 为设计验收目标；触控区不小于 44 × 44 CSS px 等效尺寸。
- 不依赖动画理解结果；状态与错误同时使用文字表达。

### 11.1 数字处理

- 输入按完整数值校验，不接受 `12abc`、指数写法、无穷值或超限精度；非法值不静默截断。
- 新场景金额按分、通勤时间按输入精度计算，避免浮点尾差造成伪差异；展示舍入不影响底层计算。
- 金额明细最多两位小数，通勤小时最多一位小数；小于展示精度的正差值显示“少于 0.1 小时”等，不误写为零。
- 单小时成本保留两位小数，必须带“约”；未发生时间节省时不计算该指标。
- Offer 保持现有展示和比较容差，新增输入完整性校验时必须回归原流程，不顺带改变年化假设。

## 13. 最小验证与交付顺序

### 13.1 分阶段交付

| 阶段 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- |
| A：需求评审 | 本 PRD，确认场景/公式/数据边界 | 关键口径无歧义，未决项有处理方式 |
| B：原型验证 | 三场景首页、结果结构；先做租房交互原型 | 用户理解问题和输出，主要误解被修正 |
| C：租房闭环 | 保留 Offer，新增租房输入/计算/本地保存 | 租房与兼容性验收通过，并出现真实用途证据 |
| D：预算闭环 | 新增空窗期预算、来源与隐私说明 | 预算边界与隐私验收通过 |
| E：小范围试用 | 三场景 V1，人工观察与回访 | 再决定修正、扩大试用或停止扩展 |

三个场景是目标 V1，但不要求一次性开发完再验证。阶段 C 未能证明新增场景有用时，暂停扩展并检查问题，而不是靠继续加功能解决。

### 13.2 两周验证窗口（建议，非开发工期承诺）

原型准备后，第一周邀请约 5 位近期正在做相关决定的人完成真实任务；第二周修正主要障碍，再邀请约 5 位，并回访前一批。至少 6 位具有非 Offer 场景需求，避免只验证已有功能。

- 记录：是否独立完成、卡在哪、是否理解口径、发现何种遗漏、之后是否采取实际行动。
- 提议的继续投入门槛：10 人中至少 7 人能独立完成并正确解释结果；至少 4 人能举出一次据此核实信息、调整方案或沟通的具体行为；不得有未修复的关键金额或隐私错误。
- 这些是内部小样本方向判断，不是行业标准或统计意义上的市场验证。真实行为证据不足时，先回访原因，不据此宣布产品市场匹配。
- 不收集真实薪资、存款与结果截图作为默认试用记录；经参与者同意仅记去标识的任务过程。V1 不为此新增后台埋点。

### 13.3 不作为成功指标

知识条目数量、页面数量、每日打开次数、停留时长及“看起来很有用”的评价，都不能独立证明产品帮助了决策。
